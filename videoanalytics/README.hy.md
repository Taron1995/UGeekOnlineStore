# videoanalytics - մարդկանց և հաստոցների ակտիվության օֆլայն վերլուծություն բազմօրյա տեսահսկման ձայնագրությունների համար

English: [README.md](README.md)

Աշխատում է արդեն ունեցած տեսագրությունների վրա (բազմաթիվ տեսախցիկների բազմօրյա ձայնագրություններ), լիովին օֆլայն՝

| Քայլ | Ինչ է անում | Բաղադրիչ |
|---|---|---|
| նմուշառում | յուրաքանչյուր ֆայլից 2-3 կադր/վ, ըստ ցանկության՝ օրվա ժամերի ֆիլտր | OpenCV |
| դարպաս | դետեկտորը բաց է թողնվում, քանի դեռ տեսարանը անշարժ է (նորից ստուգում է ամեն 3 վ) | կադրերի տարբերություն |
| հայտնաբերում | մարդիկ | YOLOX-tiny, ONNX Runtime (CPU) |
| հետևում | ID-ներ՝ արագության կանխատեսմամբ, որպեսզի 2-3 կադր/վ-ի դեպքում էլ աշխատի | սեփական կոդ (`tracker.py`) |
| իրադարձություններ | մարդու հայտնվելը, գոտու մուտք/ելք + մնալու տևողություն, հաշվարկային գծի in/out | կոնֆիգի պոլիգոններ/գծեր |
| հաստոց | WORK / IDLE՝ հաստոցի գոտում շարժման հիման վրա, մարդիկ դիմակավորված են | կադրերի տարբերություն + հիստերեզիս |
| ելք | ֆայլ-առ-ֆայլ SQLite shard-եր -> `analytics.db`, `report.html`, CSV-ներ, կադր + կլիպ հաստոցի վիճակի յուրաքանչյուր փոփոխության համար | |

Առանց դեմքի ճանաչման, առանց ամպի, առանց AGPL/GPL կոդի (տե՛ս *Լիցենզիաներ*)։

## Արագ մեկնարկ

```
pip install -e .                                   # կամ՝ pip install -r requirements.txt
python -c "import urllib.request as u; u.urlretrieve('https://github.com/Megvii-BaseDetection/YOLOX/releases/download/0.1.1rc0/yolox_tiny.onnx','yolox_tiny.onnx')"
cp cameras.example.yaml cameras.yaml               # տեսախցիկների անունները պետք է առկա լինեն ֆայլերի ուղիներում

python -m videoanalytics scan --config cameras.yaml --videos D:/footage --model yolox_tiny.onnx   # ֆայլեր, ժամանակային նշումներ, աշխատանքի ժամանակի գնահատական
python -m videoanalytics snap --config cameras.yaml --videos D:/footage --out out                 # out/snap/<camera>.jpg՝ ցանցով -> գծեք գոտիները
python -m videoanalytics run  --config cameras.yaml --videos D:/footage --model yolox_tiny.onnx --out out --limit-files 4   # փորձնական գործարկում
python -m videoanalytics run  --config cameras.yaml --videos D:/footage --model yolox_tiny.onnx --out out                    # ամբողջ նյութը
```
`out/report.html`-ը արդյունքն է։ `run`-ը կարելի է կանգնեցնել (Ctrl+C) և նորից գործարկել․ ավարտված ֆայլերը բաց են թողնվում։

## Տեսագրությունների դասավորությունը

Ցանկացած պանակային ծառ, որոնվում է ռեկուրսիվ։ Յուրաքանչյուր **հարաբերական ուղուց** վերականգնվում է երկու բան՝

* **տեսախցիկ (camera)** - կոնֆիգում նշված տեսախցիկի անունը պետք է հանդիպի որպես ամբողջական բառ (`cam1`-ը համընկնում է `cam1_...mp4`-ի և `/cam1/`-ի հետ, բայց ոչ `cam10`-ի կամ `webcam1`-ի)։
  Այլ անվանակարգի դեպքում տեսախցիկին ավելացրեք `match: "regex"`։
* **մեկնարկի ժամանակ** - ճանաչվում են՝ `20261001_080000`, `2026-10-01_08-00-00`, `2026-10-01_08.00.00`, `20261001080000`, ինչպես նաև
  ամսաթվով պանակ + ժամով ֆայլի անուն (`2026-10-01/cam1/08-00-00.mp4`)։ Մնացած դեպքերում՝ `--time-regex` (6 խումբ՝ Y m d H M S)։
  Եթե ժամանակ չի գտնվում, օգտագործվում է ֆայլի փոփոխման ժամանակը, և `scan`-ը զգուշացնում է։ Ժամանակները դիտարկվում են որպես տեղական (պատի ժամացույցի) ժամանակ՝ ժամային գոտիները հաշվի չեն առնվում։

`scan`-ը տպում է ֆայլերը ըստ տեսախցիկի, տեսանյութի ժամերը, ամսաթվերի տիրույթը և բոլոր խնդիրները (չհամընկնող ֆայլեր, առանց ժամանակային նշման, չբացվող/վնասված ֆայլեր)։
**Գործարկեք այն առաջինը** և ստուգեք, որ ամսաթվերի տիրույթը համապատասխանում է Ձեր սպասելիքին։

## Կոնֆիգուրացիա (`cameras.yaml`)

Տե՛ս `cameras.example.yaml`։ Բոլոր կոորդինատները նորմալացված են (x, y՝ 0..1)․ `snap`-ը յուրաքանչյուր տեսախցիկի մեկ կադրի վրա գծում է 10 % ցանց և կոնֆիգում նշված գոտիները,
որպեսզի կարողանաք կոորդինատները կարդալ և ստուգել։

* `options`՝ `fps` (վերլուծվող կադրեր/վ, լռելյայն՝ 3), `conf`, `active_hours` (օրինակ՝ `[[8, 20]]`, `[[22, 6]]`՝ անցնում է կեսգիշերը),
  `gate_motion`, `keepalive_s`, `clips`, `max_clips_per_file`։ Մեծ մասը կարելի է վերասահմանել հրամանի տողում (`--fps`, `--hours 8-20`, `--no-gate`)։
* ըստ տեսախցիկի՝ `zones` (աշխատատեղեր/տարածքներ), `lines` (հաշվարկ․ `in` = p1->p2 ուղղության աջ կողմից ձախ կողմ հատում),
  `machine` (պոլիգոն + `motion_thr`, `window_s`)։

## Ելք

| Ֆայլ | Բովանդակություն |
|---|---|
| `report.html` | ընդհանուր ակնարկ ըստ տեսախցիկի, ժամ × օր ջերմային քարտեզներ (մարդիկ, հաստոցի աշխատանք %), ամենաերկար պարապուրդները՝ կադրով + կլիպով |
| `hourly.csv` | տեսախցիկ, ամսաթիվ, ժամ, վերլուծված րոպեներ, միջին/առավելագույն մարդիկ, հայտնվելներ, հատում in/out, հաստոցի աշխատանքի/պարապուրդի րոպեներ |
| `events.csv` | ամեն իրադարձություն բացարձակ ժամանակով, `idle_periods.csv`, `analytics.db` (SQLite՝ `events`, `minutes`, `files`) |
| `clips/<camera>/` | `.jpg` կադր + `.mp4` (OpenCV `mp4v`՝ նվագարկվում է VLC / Windows Media Player-ով, բայց ոչ անմիջապես բրաուզերում) |

## Արագություն - պլանավորեք սկսելուց առաջ

Չափված է 4 vCPU ամպային sandbox-ում, YOLOX-tiny 416․ **65 մվ մոդելի մեկ ինֆերենս 1 թելով (82 մվ մեկ կադրի համար՝ ներառյալ չափափոխումը և NMS-ը), 29 մվ՝ 4 թելով**,
ուստի N միաթել աշխատող պրոցեսները (ինչ անում է `run`-ը, `--workers`, լռելյայն = պրոցեսորի միջուկների քանակը) ավելի լավ արդյունք են տալիս, քան մեկ բազմաթել պրոցեսը։
640x360 թեստային ֆայլը արժեցել է 0,24 պրոցեսորային վայրկյան մեկ տեսանյութային վայրկյանի համար՝ 3 կադր/վ-ի դեպքում, երբ դետեկտորը աշխատում է յուրաքանչյուր նմուշառված կադրի վրա։
Իրական արժեքը կախված է լուծաչափից և կոդեկից (1080p H.264/H.265-ի դեկոդավորումը կարող է գերակշռել), ուստի
**`scan --model yolox_tiny.onnx`-ը չափում է Ձեր ֆայլերից մեկը և տպում է ամբողջ նյութի համար աշխատանքի ժամանակի վերին գնահատականը**։

Լծակներ՝ ամենակարևորից սկսած․ `--hours` (վերլուծել միայն աշխատանքային ժամերը), `--fps` (2՝ 3-ի փոխարեն), շարժման դարպասը (լռելյայն միացված է․ նրան վստահելուց առաջ
համեմատեք `--no-gate`-ի հետ մեկ ժամվա վրա՝ շատ հանգիստ տեսարանում այն կարող է բաց թողնել փոքր և արագ շարժվող մարդուն), `--hw-decode` (OpenCV-ի միջոցով փորձում է D3D11VA/VAAPI․
այստեղ չի փորձարկվել, sandbox-ում GPU չկա), ավելի շատ աշխատող պրոցեսներ կամ GPU-ով սարք։
`yolox_s.onnx`-ը (640 px․ նույն ներբեռնման հասցեն, ֆայլի այլ անուն) ճշգրտության բարելավումն է․ նույն թեստային կադրի վրա գտել է նույն 7 մարդկանց ավելի բարձր գնահատականներով
(ամենաթույլը՝ 0,50 vs 0,39), բայց տևել է **284 մվ vs 82 մվ մեկ կադրի համար (3,5 անգամ)**։ Դետեկտորը մուտքի չափը կարդում է մոդելի ֆայլից։

## Ինչն է ստուգվել և ինչը՝ ոչ

* Դետեկտորի դեկոդավորումը/NMS-ը իրական հետիոտնային տեսանյութի վրա (OpenCV-ի նմուշ `vtest.avi`, 768x576)․ դիտարկված կադրերում տուփերը նստում են բոլոր տեսանելի մարդկանց վրա։
* Թրեքերը նույն 80 վ կտորի վրա․ պարզ IoU համընկնումը տվել է 56 ID 10 կադր/վ-ի դեպքում և 163՝ 3,3 կադր/վ-ի դեպքում (մասնատում)։ Արագության կանխատեսմամբ +
  հեռավորության անցումով՝ **28 / 26 / 28 / 26 ID 10 / 5 / 3,3 / 2 կադր/վ-ի դեպքում**, տեսադաշտում միջին մարդկանց քանակը՝ 5,8 / 5,8 / 5,8 / 5,7։ Մարդկանց իրական թվի համար
  հիմնավոր ճշմարտություն (ground truth) չկա, ուստի հաստատված է միայն *կայունությունը կադրերի հաճախականության փոփոխության դեպքում*։
  Գծի հաշվարկները նույնպես կայուն են (14 in / 18 out 10 կադր/վ-ի դեպքում, 14 / 17՝ 3,3 կադր/վ-ի դեպքում)։
* Հաստոցի WORK/IDLE-ը **շարժման ցուցիչ է, ոչ թե հաստոցի ազդանշան**․ այն կարդում է «շարժում այս գոտում»՝ մարդկանց դիմակավորմամբ։ Իմաստալից է միայն այնտեղ,
  որտեղ հաստոցը տեսանելիորեն շարժվում է․ `motion_thr`/`window_s`-ը կարգավորեք յուրաքանչյուր հաստոցի համար՝ հայտնի ժամի վրա։ Իրական հաստոցների դեմ չի վավերացվել։
* Ձեր տեսախցիկների վրա ընդհանրապես չի վավերացվել (գիշեր/IR, փակվածություն, խտություն)։ Թվեր նշելուց առաջ չափեք ձեռքով հաշված նմուշային ժամի վրա։
* «Հայտնվելներ»-ը հաշվում է հաստատված թրեքերը․ թրեքերը վերսկսվում են ամեն ֆայլում, ուստի ֆայլի սահմանին կանգնած մարդը հաշվվում է երկու անգամ։
* Յուրաքանչյուր ֆայլի առաջին `window_s` վայրկյանները չեն հաշվվում որպես հաստոցի աշխատանք/պարապուրդ (վիճակին անհրաժեշտ է լրիվ պատուհան)։

Ultralytics YOLOv5/v8/11-ը միտումնավոր **չեն** օգտագործվում (AGPL-3.0)։ Մատակարարելուց առաջ ստուգեք մոդելի կշիռների մարզման տվյալների պայմանները․
դրանցից խուսափելու համար մոդելը մարզեք (fine-tune) Ձեր սեփական տեսագրությունների վրա (այս MVP-ի մաս չէ)։
