# videoanalytics - մարդկանց, հաստոցների և նախապատրաստվածքների օֆլայն վերլուծություն բազմօրյա տեսահսկման ձայնագրությունների համար

English: [README.md](README.md)

Աշխատում է արդեն ունեցած ձայնագրությունների վրա (բազմօրյա նյութ, բազմաթիվ տեսախցիկներ), լիովին օֆլայն, միայն տեսախցիկներով (առանց հաստոցների սենսորների)։

| # | Ցուցանիշ | Ինչպես է չափվում | Կոնֆիգի բանալի | Կարգավիճակ |
|---|---|---|---|---|
| 1 | **Ժամանակը հաստոցի մոտ** | մարդու հայտնաբերում + կայանի շուրջ գոտի, զբաղվածությունը րոպեներով (կարճ «պահման» ժամանակը լրացնում է հայտնաբերման բացթողումները) | `zones` | ստուգված (սինթետիկ + իրական վիդեո) |
| 2 | **Բացակայություն ընդմիջումներից դուրս** | նույն գոտին + աշխատանքի/ընդմիջումների `schedule`․ հաշվվում են միայն այն րոպեները, երբ մարդ պետք է լինի | `schedule` | ստուգված (սինթետիկ, թեստերով) |
| 3 | **2+ աշխատողի հավաքներ** | իրար մոտ գտնվող մարդիկ (`dist_k` × մարմնի բարձրությունից պակաս), աշխատանքային գոտիներից դուրս, `min_duration_s`-ից երկար․ ապացույց՝ կադր + կլիպ | `gathering` | ստուգված իրական նյութի վրա․ շեմերը չկալիբրացված |
| 4 | **Հաստոցի աշխատանք / պարապուրդ** | ազդանշանային լամպի գույն (կանաչ/դեղին/կարմիր, HSV) **կամ** շարժում հաստոցի աշխատանքային մասի փոքր գոտում, մարդիկ դիմակավորված | `machines` | լամպը և շարժումը ստուգված սինթետիկ վիդեոյով, **իրական հաստոցների վրա՝ ոչ** |
| 5 | **Նախապատրաստվածքների քանակ** | RF-DETR՝ մարզված Ձեր մասի վրա + թրեքեր + `supervision.LineZone` հաստոցի ելքի մոտ․ **այլընտրանք**՝ հաստոցի ցիկլեր (շարժում -> կանգ = մեկ մշակում) | `workpieces`, `machines[].cycle` | հաշվարկը ստուգված COCO կշիռներով իրական վիդեոյի վրա և խաղալիք մարզմամբ․ **Ձեր մասերի համար պետք են Ձեր annotation-ները** |
| 6 | **Նստած՝ առանց շարժման** | մարդու մարմնի ակտիվությունը ժամանակի ընթացքում․ կադրերի տարբերություն (լռելյայն) կամ MediaPipe Pose (կետեր + դիրք) | `inactivity` | շարժման մեթոդը ստուգված իրական վիդեոյի վրա․ pose-ը չափված է, տե՛ս ստորև զգուշացումը |
| 7 | Մարդկանց հաշվարկ | թրեքեր + հաշվարկային գծեր (in / out), եզակի հայտնվելներ | `lines` | ստուգված (իրական վիդեո, կայուն 2-10 կադր/վ-ի դեպքում) |

Ամեն ինչ օֆլայն է․ միայն ազատ լիցենզիաներ (տե՛ս *Լիցենզիաներ*)։ Առանց դեմքի ճանաչման։

## Տեղադրում

```
pip install -e .                    # հիմք՝ մարդիկ, գոտիներ, ժամանակացույց, լամպ, շարժում, հավաքներ, ցիկլեր, անշարժություն (շարժման մեթոդ)
pip install -e ".[pose]"            # + MediaPipe Pose՝ inactivity.method: pose-ի համար
pip install -e ".[workpieces]"      # + RF-DETR և supervision (տեղադրում է PyTorch)՝ նախապատրաստվածքների հաշվարկի համար
pip install -e ".[train]"           # + ինչ պետք է RF-DETR-ը Ձեր մասերի վրա մարզելու համար
```
Python 3.10+։ MediaPipe-ը ունի wheel-ներ Windows-ի (x64/ARM), Linux-ի և macOS-ARM-ի համար։ Linux-ում պետք է նաև `sudo apt install libegl1 libgles2`։

**PyCharm:** բացեք `videoanalytics` թղթապանակը (որտեղ `pyproject.toml`-ն է) որպես նախագիծ, ստեղծեք virtualenv, PyCharm-ի տերմինալում կատարեք վերևի `pip install` տողը,
ապա բացեք `run_pipeline.py`-ը, փոխեք վերևի հաստատունները (`VIDEOS`, `CONFIG`, ...), ընտրեք `STEP`, սեղմեք Run։
Տերմինալից ամեն ինչ `python -m videoanalytics <command> --help` է։

## Աշխատանքային ընթացք

```
python -m videoanalytics models --pose                              # ներբեռնում է models/yolox_tiny.onnx (+ MediaPipe pose մոդելը)
cp cameras.example.yaml cameras.yaml                                # տեսախցիկների անունները պետք է առկա լինեն ֆայլերի ուղիներում
python -m videoanalytics scan --config cameras.yaml --videos D:/footage --model models/yolox_tiny.onnx   # ֆայլեր, ժամանակային նշումներ, աշխատանքի ժամանակի գնահատական
python -m videoanalytics snap --config cameras.yaml --videos D:/footage --out out                         # out/snap/<camera>.jpg՝ ցանց, գոտիներ, լամպի գույն
python -m videoanalytics run  --config cameras.yaml --videos D:/footage --model models/yolox_tiny.onnx --out out --limit-files 4   # փորձնական գործարկում
python -m videoanalytics run  --config cameras.yaml --videos D:/footage --model models/yolox_tiny.onnx --out out                    # ամբողջ նյութը
python -m videoanalytics report --config cameras.yaml --out out     # վերակառուցել հաշվետվությունը (օր.՝ ժամանակացույցը փոխելուց հետո)
```
`out/report.html`-ը արդյունքն է։ `run`-ը կարելի է կանգնեցնել (Ctrl+C) և նորից գործարկել․ ավարտված ֆայլերը բաց են թողնվում։ Ժամանակացույցը ազդում է միայն
հաշվետվության վրա, ուստի կարող եք փոխել այն և նորից կատարել `report`՝ առանց որևէ վիդեո նորից մշակելու։

## Տեսագրությունների դասավորությունը

Ցանկացած պանակային ծառ, որոնվում է ռեկուրսիվ։ Յուրաքանչյուր **հարաբերական ուղուց** վերականգնվում է երկու բան՝

* **տեսախցիկ (camera)** - կոնֆիգում նշված տեսախցիկի անունը պետք է հանդիպի որպես ամբողջական բառ (`cam1`-ը համընկնում է `cam1_...mp4`-ի և `/cam1/`-ի հետ,
  բայց ոչ `cam10`-ի կամ `webcam1`-ի)։ Այլ անվանակարգի դեպքում տեսախցիկին ավելացրեք `match: "regex"`։
* **մեկնարկի ժամանակ** - ճանաչվում են՝ `20261001_080000`, `2026-10-01_08-00-00`, `2026-10-01_08.00.00`, `20261001080000`, ինչպես նաև ամսաթվով պանակ + ժամով ֆայլի
  անուն (`2026-10-01/cam1/08-00-00.mp4`)։ Մնացած դեպքերում՝ `--time-regex` (6 խումբ՝ Y m d H M S)։ Եթե ժամանակ չի գտնվում, օգտագործվում է ֆայլի փոփոխման
  ժամանակը, և `scan`-ը զգուշացնում է։ Ժամանակները դիտարկվում են որպես տեղական (պատի ժամացույցի) ժամանակ՝ ժամային գոտիները հաշվի չեն առնվում։

`scan`-ը տպում է ֆայլերը ըստ տեսախցիկի, տեսանյութի ժամերը, ամսաթվերի տիրույթը, յուրաքանչյուր տեսախցիկի համար կարգավորված ֆունկցիաները և բոլոր խնդիրները
(չհամընկնող ֆայլեր, առանց ժամանակային նշման, չբացվող ֆայլեր)։ **Գործարկեք այն առաջինը։**

## Կոնֆիգուրացիա

`cameras.example.yaml`-ը մեկնաբանություններով ցույց է տալիս բոլոր ֆունկցիաները։ Կոորդինատները նորմալացված են (x, y՝ 0..1)․ `snap`-ը գծում է 10 % ցանց։
**Ամեն բանալի ստուգվում է մեկնարկին** (անհայտ բանալիներ, պիքսելներով տրված պոլիգոններ, գոյություն չունեցող գոտուն կապված հաստոց, ...) և բոլոր խնդիրները
հաղորդվում են միասին։

* `zones`՝ `kind: workstation` (լռելյայն․ սպասվում է, որ համալրված է, բացառվում է հավաքներից) կամ ցանկացած այլ տեսակ, օր.՝ `rest`։ `hold_s` (լռելյայն 5)՝ վերջին
  հայտնաբերումից հետո գոտին այդքան ժամանակ «զբաղված» է համարվում։
* `schedule` (գլոբալ, ըստ տեսախցիկի կամ ըստ գոտու)՝ `work` և `breaks` որպես `["HH:MM", "HH:MM"]` զույգեր (գիշերային միջակայքերը աշխատում են), `days` (երկուշաբթի = 1)։
  Բացակայություն = աշխատանքային ժամերի ներսում, ընդմիջումներից դուրս այն րոպեները, երբ աշխատատեղի գոտին (գրեթե) դատարկ էր։ Առանց ժամանակացույցի ստանում եք միայն
  «ժամանակը կայանի մոտ»։ Հանգստի գոտիները երբեք բացակայություն չեն ստանում։
* `machines` (մեկ տեսախցիկում՝ մի քանիսը)՝ `source: lamp` - `roi`-ն լամպի սյան շուրջ խիտ պոլիգոն է, `work_colors` (լռելյայն `[green]`), `sat_min` / `val_min` /
  `min_frac`-ը կարգավորեք `snap`-ով, որը կադրի վրա տպում է ընթերցողի տեսած գույնը և գույների գնահատականները․ կարմիր ժամանակը հաշվետվության մեջ «ահազանգ» է, դեղինը՝ «սպասում»։
  `source: motion` - `roi`-ն ծածկում է շարժվող մասը (spindle, սեղան), `motion_thr`, `window_s`, `on_frac`։ `zone:`-ը կապում է օպերատորի գոտին․ այդ դեպքում
  հաշվետվությունը ցույց է տալիս աշխատանքը **առանց օպերատորի**։ `cycle:`-ը հաշվում է ցիկլերը (շարժման հաստոցները օգտագործում են իրենց կարճ պատուհանը․
  դրեք տեսախցիկի մակարդակի `fps: 5`, որպեսզի մի քանի վայրկյանանոց ցիկլը լուծվի)։
* `gathering`՝ `min_people` (2), `dist_k` (1,0 × մարմնի միջին բարձրություն), `min_duration_s` (180), `gap_s` (10․ հայտնաբերման բացթողումները լրացվում են)։
* `inactivity`՝ `method: motion | pose`, `zones` (հետևել միայն այս գոտիների մարդկանց), `min_duration_s`, `motion_thr`, `require_seated` (միայն pose)։
* `workpieces`՝ `weights`, `classes`, `threshold`, `line`, `count: in | out | both`, `model: nano | small | medium | large`։
* տեսախցիկի մակարդակի `fps`-ը այդ տեսախցիկի համար վերասահմանում է `options.fps`-ը (ցիկլերի և նախապատրաստվածքների համար պետք է 4-6)։

## Նախապատրաստվածքների հաշվարկ. Ձեր նյութից մինչև թվեր

RF-DETR-ին պետք է սովորեցնել, թե ինչ տեսք ունի *Ձեր* մասը․ այստեղ ոչինչ չի կարող փոխարինել նրա annotation-ված օրինակներին։

```
python -m videoanalytics frames --config cameras.yaml --videos D:/footage --camera cam3 --count 400 --out dataset/raw   # ամբողջ օրերի վրա տարածված կադրեր
#   annotation արեք dataset/raw-ը CVAT / Label Studio / Roboflow-ում (մեկ դաս, օր.՝ "workpiece"), արտահանեք COCO
python -m videoanalytics split-coco --images dataset/raw --annotations instances.json --out dataset
python -m videoanalytics train --dataset dataset --model nano --epochs 50 --out output       # պետք է ".[train]"․ օգտագործեք GPU
#   -> ստուգում է checkpoint_best_total.pth-ը և last_ema.pth-ը Ձեր validation նկարների վրա (recall / precision) և տպում է օգտագործելիքը՝
#      workpieces: {weights: ..., classes: [workpiece], line: ...}
```
Հաշվարկային գիծը դրվում է այնտեղ, որտեղ մասերը դուրս են գալիս հաստոցի գոտուց։ `in`-ը `p1 -> p2` ուղղության աջ կողմից ձախ կողմ հատումն է (նույն կանոնը, ինչ մարդկանց
գծերինը)։ Հաշվարկի համար օգտագործվում է `supervision.LineZone`-ը․ `supervision.ByteTrack`-ը **չի** օգտագործվում․ այն deprecated է և հանվում է supervision 0.31-ում,
ուստի track id-ները տալիս է պահոցի սեփական թրեքերը։ Օգտագործեք Apache-2.0 չափերը (nano/small/medium/large)․ RF-DETR XL / 2XL-ը PML լիցենզիայի տակ է և չի բացահայտվում։

Եթե դեռ չեք կարող annotation անել, հաշվեք **հաստոցի ցիկլերը** (`machines[].cycle`)․ մեկ շարժում -> կանգ = մեկ մշակում։ Դա մարզում չի պահանջում, բայց հավասար է
մասերի քանակին միայն եթե մեկ ցիկլը մեկ մաս է տալիս։

## Կալիբրացիա (արեք սա՝ նախքան թվերին վստահելը)

* **Լամպ**․ `snap`-ը կադրի վրա ցույց է տալիս հայտնաբերված գույնը և գնահատականները։ Գերլուսավորված լամպերը տեսախցիկում սպիտակ են երևում․ իջեցրեք `sat_min`-ը, նեղացրեք ROI-ն։
* **Հաստոցի շարժում**․ `motion_thr` / `window_s` ըստ հաստոցի՝ մի ժամի վրա, որի իրական վիճակը գիտեք։
* **Անշարժություն**․ `python -m videoanalytics probe --config cameras.yaml --videos D:/footage --camera cam2 --model models/yolox_tiny.onnx --start 600 --seconds 120`
  տպում է յուրաքանչյուր մարդու չափված ակտիվությունը։ Գործարկեք այնտեղ, որտեղ ինչ-որ մեկը անշարժ նստած է, և այնտեղ, որտեղ աշխատում է, ապա `motion_thr`-ը դրեք երկուսի միջև։
  Իրական հետիոտնների վրա կադրերի տարբերության ակտիվությունը քայլելիս 0,4-0,7 էր․ անշարժ մարդու վրա, երբ ավելացվել էր վիդեոյի սեղմման աղմուկ, այն ճիշտ 0 էր։
  Լռելյայն 0,01 շեմը մեկնարկային կետ է, ոչ թե նստած աշխատողի չափում։
* **Pose-ի զգուշացում**․ 60-83 px բարձրությամբ մարդկանց վրա (լայն տեսախցիկների համար բնորոշ) MediaPipe-ը 7 կտրվածքից 5-ում է գտել կմախք, և *նույն անշարժ մարդու* վրա՝
  միայն սեղմման աղմուկ ավելացնելով, pose-ի ակտիվության մեդիանը 0,02 էր, իսկ 95-րդ պերցենտիլը՝ մարմնի բարձրության 0,25-ը․ այդ չափի դեպքում pose-ը չի տարբերում
  «անշարժը» «շարժվողից»։ Դրա համար է `motion`-ը լռելյայնը։ `pose`-ն օգտագործեք միայն մոտ պլանով տեսախցիկների համար (մեծ մարդիկ)․ այդ դեպքը չկարողացա չափել։
* **Հավաքներ**․ կողք-կողքի քայլող երկու մարդ նույնպես որակավորվում է, եթե `min_duration_s` ժամանակ մնում են իրար մոտ․ բարձրացրեք այն (լռելյայնը 3 րոպե է)։

## Արագություն - պլանավորեք սկսելուց առաջ

Չափված է 4 vCPU ամպային sandbox-ում․ YOLOX-tiny 416-ը **մոդելի մեկ ինֆերենսի համար տևում է 65 մվ 1 թելով (82 մվ մեկ կադրի համար՝ ներառյալ չափափոխումը և NMS-ը), 29 մվ՝ 4 թելով**,
ուստի N միաթել աշխատող պրոցեսները (ինչ անում է `run`-ը, `--workers`, լռելյայն = պրոցեսորի միջուկների քանակը) ավելի լավ արդյունք են տալիս, քան մեկ բազմաթել պրոցեսը։
640x360 թեստային ֆայլը արժեցել է 0,24 պրոցեսորային վայրկյան մեկ տեսանյութային վայրկյանի համար՝ 3 կադր/վ-ի դեպքում, երբ դետեկտորը աշխատում է յուրաքանչյուր նմուշառված
կադրի վրա։ Իրական արժեքը կախված է լուծաչափից և կոդեկից (1080p H.264/H.265-ի դեկոդավորումը կարող է գերակշռել), ուստի
**`scan --model ...`-ը չափում է Ձեր ֆայլերից մեկը և տպում է աշխատանքի ժամանակի վերին գնահատականը**։

Չափված այլ ծախսեր․ RF-DETR nano (384 px)՝ ~180-200 մվ մեկ կադրի համար այդ պրոցեսորով (օգտագործեք միայն մասեր հաշվող տեսախցիկների համար՝ `--workers 1-2`-ով, PyTorch-ը
օգտագործում է բոլոր միջուկները և ~1 GB RAM մեկ պրոցեսի համար)․ MediaPipe pose՝ 37-43 մվ մեկ մարդու կտրվածքի համար։

Լծակներ՝ ամենակարևորից սկսած․ `--hours` (միայն աշխատանքային ժամերը), `--fps`, շարժման դարպասը (լռելյայն միացված է․ նրան վստահելուց առաջ համեմատեք `--no-gate`-ի հետ մեկ ժամվա
վրա), `--hw-decode` (D3D11VA/VAAPI՝ OpenCV-ի միջոցով․ այստեղ չի փորձարկվել), ավելի շատ աշխատող պրոցեսներ կամ GPU-ով սարք։ `models --yolox-s`-ը տալիս է ավելի ճշգրիտ
մարդկանց դետեկտոր փոքր մարդկանց համար (284 մվ ընդդեմ 82 մվ մեկ կադրի համար, 3,5 անգամ)։

## Ինչն է ստուգվել և ինչը՝ ոչ

Ստուգված է (սինթետիկ վիդեո՝ հայտնի պատասխաններով, ինչպես նաև OpenCV-ի նմուշ `vtest.avi`, 768x576 հետիոտններ)․

* Մարդկանց դետեկտորի դեկոդավորումը/NMS-ը․ թրեքերը 80 վ կտորի վրա՝ 28 / 26 / 28 / 26 ID 10 / 5 / 3,3 / 2 կադր/վ-ի դեպքում (պարզ IoU համընկնումը տվել է 56 և 163)․ գծի հաշվարկները կայուն են (14 in / 18 out 10 կադր/վ-ի դեպքում)։
* RF-DETR nano + թրեքեր + `supervision.LineZone` նույն կտորի վրա՝ **14 in / 18 out**, ճիշտ նույնը, ինչ YOLOX + պահոցի սեփական գիծը։
* Train -> load -> count RF-DETR-ով խաղալիք սինթետիկ տվյալների վրա (24 նկար, nano, CPU, մոտ մեկ րոպե մեկ epoch-ի համար)․ `split-coco`-ի ելքը ընդունվում է, `train`-ը գրում է
  checkpoint-ները, `from_checkpoint`-ը վերականգնում է դասերի անունները։ 10 epoch-ից հետո `last_ema.pth`-ը գտնում է մասը 0,85-0,88 վստահությամբ և տուփերով՝ իրականից մեկ պիքսելի
  սահմաններում, իսկ հաշվարկային գիծը տալիս է ճիշտ մեկ `in` դրա վրայով սահող մասի համար։ **Բայց** `checkpoint_best_total.pth`-ը (գրադարանի «լավագույնը ըստ validation mAP»)
  գրեթե չմարզված 0-րդ epoch-ի կշիռներն էին՝ mAP-ը հագեցվում է 1,0-ում այդպիսի չնչին տվյալների վրա, և 0,5 վստահության դեպքում ոչինչ չգտավ (recall 0 %)։ Դրա համար
  `train`-ը հիմա փորձարկում է երկու թեկնածուին Ձեր validation նկարների վրա և առաջարկում է մեկը։
* Լամպի գույներ (կանաչ/դեղին/կարմիր, թարթող), շարժման հաստոց, ցիկլեր, հավաքներ, զբաղվածություն, ժամանակացույց/բացակայություն, պարապուրդի հատվածներ, հաշվետվության թվեր․
  unit թեստեր՝ մուտացիոն ստուգումներով (թեստերը ձախողվում են, երբ տրամաբանությունը դիտավորյալ փչացվում է)։
* Հավաքները իրական նյութի վրա․ աշխատանքային գոտուց դուրս խմբերը գտնվում են, և ապացույցի կադրը ցույց է տալիս դրանք։

**Ստուգված չէ՝** որևէ բան Ձեր տեսախցիկների վրա (գիշեր/IR, փակվածություն, բազմություն, լամպի գերլուսավորում)․ հաստոցի WORK/IDLE-ը իրական հաստոցների դեմ (դա շարժման /
լամպի ցուցիչ է, ոչ թե հաստոցի ազդանշան)․ pose մեթոդը մեծ մարդկանց վրա․ նախապատրաստվածքների իրական ճշգրտությունը․ `--hw-decode`-ը․ Windows-ը (այստեղ ոչինչ Windows-ում չի աշխատել)։
Թվեր նշելուց առաջ չափեք ձեռքով հաշված նմուշային ժամի վրա։

Հայտնի սահմանափակումներ․ թրեքերը վերսկսվում են ամեն ֆայլում, ուստի ֆայլի սահմանին կանգնած մարդը հաշվվում է երկու անգամ (հայտնվելները, հավաքները, անշարժությունը կարող են
կտրվել)․ ամեն ֆայլի առաջին `window_s` վայրկյանները չեն հաշվվում որպես հաստոցի աշխատանք/պարապուրդ․ բացակայությունը պահանջում է, որ գոտու պոլիգոնը ծածկի այն տեղը, որտեղ
մարդը իսկապես կանգնում է (ոտքերի կետը)։
